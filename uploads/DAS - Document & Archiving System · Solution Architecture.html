§ 03 — Information ArchitectureThe code is the architecture

The Fund does not need a taxonomy invented for it. Its Document & Records Control Guide already defines a unified code, and its records register already assigns one to every series. The system's job is to generate that code, not to ask a user to type it — and then to let every segment of it do work.

§ 04 — Data FlowThe life of a record, and the gates that move it

The Executive Regulation does not describe a repository. It describes a journey with three custody phases and two irreversible decisions. Modelling it as a status column would satisfy a demo and fail an audit; modelling it as physical movement between storage tiers with an approval gate at each boundary is what the law actually requires.

Ingestion pipeline

All four capture channels converge on one drop-off library, so there is a single place where classification, coding and virus scanning happen — and a single audit point.

StepActionComponentFailure behaviour
1Arrival — scan station, SMTP-enabled library, watched folder, or REST bulk APICapture serviceRejected item stays in an exception queue with reason; sender notified
2Malware scan before any processingSharePoint-aware AVQuarantine, alert to SOC
3OCR and rendition to searchable PDF/A-2b; original preserved alongsideOCR engineLow-confidence pages flagged for manual re-scan, not silently indexed
4Metadata extraction — dates, reference numbers, correspondent, entitiesExtraction serviceBlank fields left for the originator; never guessed into a mandatory field
5Classification proposal — rules first, statistical model secondClassification serviceBelow confidence threshold → routed to the originator to classify
6Human confirmation of series, confidentiality and Information OwnerDrop-off formItem cannot leave drop-off until mandatory fields are complete
7Code reservation and assignmentDocument ID providerSequence is transactional; gaps are logged, never re-used
8Routing to the destination site and libraryContent OrganizerUnmatched rule → holding library + records officer task
9Retention rule bound; Date archived stamped; item indexedPolicy + searchRule binding failure blocks declaration and raises an incident
10Audit event written and forwarded to SIEMAudit pipelineAudit write failure fails the operation — never a silent success
Step 3 is the step most proposals omit. SharePoint Server has no OCR of its own. Without a rendition engine at ingestion, none of the ~70,000 migrated scans is full-text searchable — and "advanced search including full-text" is an explicit acceptance criterion. The engine, its licensing model (per page, per core, or per server) and the reprocessing time for the migration backlog all belong in the BOQ — and against an 8 TB corpus the reprocessing time is a schedule item, not a footnote (§07).

Retrieval flow

  1. Query enters the Search Centre; the user's identity resolves through the same AD groups used for permissions.
  2. Results are security-trimmed at query time — a user never learns that a document they cannot open exists.
  3. Refiners narrow by sector, function, year, document type and confidentiality; the record series field allows a records officer to pull an entire series in one click.
  4. Selection opens in Office Online Server for preview. For Confidential and Secret the download path is closed and the preview is the only surface.
  5. Download, where permitted, applies IRM so that protection persists outside the farm.
  6. Every view, download and print attempt writes an audit event; bulk-read patterns raise a SIEM alert.

§ 05 — Application FlowWho touches a document between upload and custody

The lifecycle in §04 spans years. This spans minutes. The design intent is that the system does the mechanical work — scanning, reading, proposing, coding, filing — and asks a human only for the two judgements a machine has no authority to make: is this classified correctly and do I approve it.

The journeys the system has to be good at

JourneyActorPathTarget
File a working documentAny employeeUpload → confirm proposed index → approve → filedUnder 60 seconds of human time
Bulk-file a scanned batchRecords clerkScan batch → separator-sheet split → batch index → single confirmation for the batchPer-batch confirmation, not per-page

Workflows in scope

  • Document approval — serial or parallel, driven by the delegation-of-authority matrix, not by hard-coded approvers.
  • Classification exception — raised when the proposal engine is below its confidence threshold or the routing rule does not match.
  • External sharing request — manager approval, expiry date mandatory, auto-revoke on expiry.
  • Disposition approval — committee vote, mandatory minute reference, generates the destruction certificate.
  • Transfer to National Archives — assembles the PDF/A package and metadata manifest, requires a signed transfer record.
  • Retention plan change — the only route by which a retention value in the register can change; five-yearly review is a scheduled instance of it.
  • Legal hold apply / release — restricted to a named role, dual-logged.

§ 07 — DeploymentPhysical topology, high availability and disaster recovery

The RFP asks for SQL Always On and Nutanix VM replication. Those are two different recovery points on two halves of the same system, and the failure case they create — a database that is current and application servers that are an hour stale — is the thing a DR drill has to prove is survivable. The recovery order is part of the design, not part of the runbook written afterwards.

The year-10 projection assumes 1 TB per year of new base content — an assumption, not a measurement, and now the only number in this table still waiting to be replaced (§11).
8 TB and 70,000 documents do not describe the same thing. Eight terabytes across seventy thousand items is an average of 120 MB per document — that is not office content, it is audio-visual and design material. The Fund's own records register anticipates exactly that: Corporate Communication holds visual and audio production material and artwork, and the National Archives retention template carries a dedicated audio-visual class for tapes, recordings, photographs and films. So either the 70,000 counts record files rather than individual documents, or the corpus is dominated by media assets. The answer changes migration duration by a factor of five and decides whether large media belongs inside SharePoint at all — see §11, question 1.

§ 10 — DecisionsThe calls that shape everything else

Eleven decisions with real alternatives. Each is recorded with what it costs, so the design review can overturn one without unpicking the rest. The last of them was decided the other way until the Fund confirmed the corpus at 8 TB.

ADR-1 · Retention runs on on-premises primitives

Alternative rejected: cloud retention labels

Microsoft Purview retention labels, auto-labelling and sensitivity labels are cloud services. On a fully on-premises farm they do not exist. Retention is therefore built on content-type information management policies, the Content Organizer and a custom disposition workflow. Cost: policy authoring is per content type rather than per label, and there is no tenant-wide policy view — the records officer console (§02) exists to fill that gap.

ADR-2 · OCR and PDF/A rendition are a bought component

Not optional — an acceptance criterion depends on it

SharePoint Server performs no optical character recognition. Without a rendition engine, scanned documents are indexed by filename and metadata only, and "full-text search" fails at UAT. PDF/A is separately mandated by the National Archives guidance for long-term preservation. Cost: a licence line, a processing tier sized for the migration burst, and reprocessing time for the backlog.

ADR-3 · K2 is the approval engine; SharePoint owns retention automation

Alternative rejected: SharePoint 2013 workflows

K2 is already deployed and already named in the integration matrix. Legacy SharePoint workflow is on a deprecation path and should not carry new business process. Retention and disposition automation stays in native timer jobs and event receivers, because it must run whether or not the workflow platform is available. Cost: a licensing check on K2 process count, and a clear boundary — K2 owns process state, the DMS owns the outcome.

ADR-4 · Two replication mechanisms, one documented recovery order

Consequence of the RFP requiring both

SQL Always On asynchronous replication gives the database a recovery point measured in seconds. Nutanix protection-domain replication gives the application VMs a recovery point measured in tens of minutes. Recovering them in the wrong order brings up stale application configuration against a current database. The order in Fig. 6 is part of the design and is what the DR drill tests. Cost: a slightly more complex runbook, in exchange for a database RPO an order of magnitude better than VM replication alone would give.

ADR-5 · Immutability comes from the storage layer

Alternative rejected: application-enforced immutability

SharePoint's record declaration prevents edit and delete through the application. The National Archives guidance calls for a non-rewritable medium, which is a stronger claim: it must hold against a farm administrator. That means WORM-capable storage or an RBS provider with immutability, with a retention lock at least as long as the longest archive retention in the register. Cost: storage procurement, and the discipline that anything written to Tier 3 genuinely cannot be corrected — so the classification gate before declaration has to be right.

ADR-6 · Content databases are partitioned by sector and lifecycle tier

Alternative rejected: one large content database

Keeping each database under the ~200 GB supported comfort limit is the immediate reason. The structural reason matters more: an archive database on its own storage tier can be moved to immutable media, backed up on its own schedule and restored without touching live division content. At 8 TB the split also unlocks a real concession — the Archive Centre is a read-mostly Records Center and therefore qualifies for the document-archive exception, so it can run a handful of very large databases while the division workspaces stay at 200 GB. Cost: roughly forty content databases to operate rather than a handful.

ADR-7 · Classification is rules-first, model-second

RFP lists AI-based recognition as "good to have"

The Fund's own classification scheme is deterministic — organisation unit, document type and process largely determine the destination. A rule set derived from the register will classify the majority correctly and is auditable, which matters in a regulated archive. A statistical model is layered on afterwards for the residue, always with a confidence threshold below which a human decides. Cost: rule maintenance as the scheme evolves — mitigated by keeping rules as data, not code.

ADR-8 · Oracle stays authoritative; the DMS links rather than copies

Alternative rejected: replicating ERP fields into metadata

Copying contract values, vendor names or PO status into document metadata creates a second version of the truth that drifts silently and that nobody is accountable for reconciling. The DMS stores the ERP reference and resolves the current values on demand. Cost: the ERP must be reachable for those fields to display, so the interface needs a cached-value fallback and a clear stale indicator.

ADR-9 · Every web application carries a Windows-authentication zone

Prerequisite disguised as a detail

If federated sign-in is the default zone, the search crawler cannot authenticate and the index stays empty — a failure that surfaces late and looks like a search problem rather than an authentication one. Each web application is extended with a Windows-authentication zone reserved for the crawl account. Cost: one extra zone and its DNS entry per web application.

ADR-10 · Libraries group series that share a metadata set

Alternative rejected: one library per record series

464 libraries would be unnavigable, would multiply configuration by an order of magnitude and would push several sites past comfortable list counts. Series sharing a metadata set and retention rule sit together, distinguished by the record series field, which is also what search refines on. Cost: the file plan and the folder structure stop being the same thing — which is correct under ISO 15489, but needs to be taught in the training material.

ADR-11 · Remote BLOB Storage is mandatory, not an optimisation

Reversed by the measured 8 TB volume

At the originally estimated ~100 GB, leaving BLOBs inside SQL Server was the simpler choice and RBS was optional. At 8 TB it is not: every full backup, every restore, every DR seed and every TDE operation would drag fifteen terabytes of binary content through SQL. Externalising BLOBs collapses the SQL footprint to metadata and pointers — roughly 0.5 TB now, 1.6 TB at year ten — so the database becomes something that can be backed up nightly and failed over in minutes, while the content itself is protected by storage-array snapshots and replication and can be tiered onto WORM media.

Cost and caveats. A supported RBS provider is a licence line. Backup and restore become a two-part operation that must stay consistent — an orphaned BLOB store and a restored database are not a working system, so the backup tooling has to understand both. And RBS does not raise the content-database size ceilings: externalised BLOBs still count toward them, so the ~40-database partitioning in ADR-6 stands either way.

Questions for the clarification round

  1. How many items make up the 8 TB, and what is their size distribution? At a 120 MB average these are media and design files; at a 2 MB average they are documents. Migration duration, OCR volume, search crawl time, the content-database count and the question of whether audio-visual masters belong inside SharePoint at all all follow from this one measurement. An item count and a file-size histogram per source repository settles it, and it is the first thing to ask for.
  2. What are the target RPO and RTO? The RFP requires them to be achieved in a drill but does not state them. They determine whether the DR design in §07 is sufficient or over-engineered.
  3. Is the National Archives interface in or out? The RFP lists external integration as optional, but transfer of permanently valuable records is a statutory obligation. Building the export packager later costs more than building it now.
  4. Which existing correspondence systems remain in service? The records register points at several — a shared file system, OneDrive, an intranet, a correspondence system, and pre-2010 hardcopy held in an office archive. Each is a separate migration decision.
  5. How many scan stations, and where? Capture tier sizing and the batch-scanning workflow depend on it.
  6. Does "external stakeholder sharing" mean authenticated guest access, or expiring links only? The two have very different security architectures.
  7. Is the records register at reference 3 the approved baseline, or a working draft? This is the single most schedule-critical answer in the list.
